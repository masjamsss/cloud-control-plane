# Lessons ledger

What the findings taught, beyond the lines they changed. A fix that closes one entry in
[`FINDINGS.md`](FINDINGS.md) and teaches nothing needs no lesson here. A fix that reveals a
*class* of mistake belongs here, so the next person does not rediscover it.

Verified by `scripts/findings-gate.sh`: every lesson must reference at least one real
finding id, so this cannot drift into unattributed folklore.

## Entry format (the gate parses the `Findings:` line — keep it)

```
### L-<n> — <one-line lesson>

Findings: CI-2, CI-8

<why it happened, and what to do differently>
```

---

### L-1 — A check that cannot run must never look like a check that passed

Findings: CI-2

`publish-gate.sh` ran `gitleaks dir`, discarded stdout and stderr, and never read the exit
status. The pinned gitleaks (v8.18.4) has no `dir` subcommand — it arrived in v8.19.0 — so
the command failed instantly, wrote no report file, and the script counted zero findings
and recorded **PASS**. The secret scanner had never scanned anything, and the green tick
said the opposite.

The version pin was the trigger; the swallowed exit status was the defect. Any wrong pin,
unreadable config, or future CLI change would have produced the same silent pass.

**Do differently:** when a gate shells out, distinguish *"ran and found nothing"* from
*"could not run"*. Here `--exit-code 0` already means findings do not affect the exit
status — so any non-zero status can only be the invocation failing, and is now a hard
failure with the tool's stderr surfaced. `2>/dev/null` on a security check is a bug.

Once it actually ran it found 4 hits, and 3 of them were the audit's own PG-5 probe rows —
the shapes the report says PG-5 misses. The report's argument for layering was correct and
had simply never been exercised.

### L-2 — Keyword rules need negative tests, or they quietly mis-file things

Findings: CI-2

The topic assignment in `FINDINGS.md` is generated by regex over finding titles. The
`resource-leak` rule matched `/leak/` — which also matches **git`leak`s**. CI-2, a finding
about a CI check that never runs, was filed under resource leaks. It was found by eye
while ticking the entry, not by any check.

**Do differently:** a classifier is code. When the rule is a substring match, test that it
does *not* match the obvious neighbours, the same way the gate's own failure modes were
each verified to trip. Cheap version: after generating, read the smallest buckets — a
mis-filed item is usually the one that looks out of place in a small group.

### L-3 — Re-anchoring citations is mechanical; deciding a finding is stale is not

Findings: IMP-7, CONC-3, CONC-14

Re-pointing 66 drifted `file:line` citations at current `main` was safely automated by
matching line *content* between the two commits. But two cases could not be: IMP-7's
subject had been fixed since the audit, and CONC-3/CONC-14's code had been rewritten
around the cited lines. Renumbering those automatically would have published a resolved
finding as live, and re-anchored two live findings without checking they still held.

**Do differently:** automate the mechanical part, and let it *fail loudly* on anything it
cannot resolve by content match — that residue is exactly the set needing judgement. Three
citations fell out, and all three turned out to be substantive rather than positional.
